# 6. Code generation by templating the shell itself

Date: 2026-09-01

## Status

Accepted

Supersedes nothing. ⚠️ `sprints/SPRINT-04.md` refers to this decision as ADR
0004; that number was taken by the three-way build cache key before Sprint 04
began.

## Context

A customer's `appconfig.json` has to become a Gradle project that compiles,
signs, and installs. There are two ways to do that, and the choice is close to
irreversible once either one has customers.

**Manipulate an abstract syntax tree.** Parse the shell's Kotlin and Gradle,
rewrite nodes, print it back. This is what a compiler would do, and it is what
sounds rigorous.

**Template the shell.** Keep the app as readable source with a handful of
placeholders, and fill them in.

Two constraints decide it. The first is that generated output must be
**byte-identical for identical input** — without that the three-way cache key
(ADR 0004) never hits, every user-triggered build is a full recompile, and the
unit economics in master spec §16 do not work. The second is that a human must
be able to open the shell and see the app that customers actually run; a
generator whose output nobody can read is a generator whose bugs nobody can
find.

## Decision

**Template the shell, and make the shell its own template.**

`shells/android` is one directory that is simultaneously:

- the app that `./gradlew assembleDebug` builds and Android Studio opens;
- the template tree the generator renders.

Files ending `.tmpl` are rendered with Scriban; everything else is copied
verbatim. The committed concrete file next to each template is _the rendering of
that template against the shell's own `appconfig.json`_, regenerated by
`tools/ApproveGolden` and asserted in CI.

Three decisions inside that are worth stating separately.

**Escaping is a property of the model, not of the call site.** `TemplateModel`
returns an object whose every string is already escaped for the file being
written, so a template author writes `{{ app.name }}` and cannot get it wrong.
The obvious alternative — helper functions like `{{ android_string app.name }}`
— works exactly as long as everyone remembers, and the failure when someone
forgets is invisible: the project generates, the golden file records the wrong
bytes, and the build breaks only for customers whose app name contains an
apostrophe.

**A template with no registered escaping rule is an error.** Not a fall back to
"no escaping". A permissive default is a vulnerability waiting for the first
template somebody adds in a hurry.

**`namespace` is constant; `applicationId` is the customer's.** These are
independent in the Android Gradle Plugin and conflating them is the trap this
generator walked into on its first real build: taking the namespace from the
config put `R` and `BuildConfig` in `com.acme.whatever` while the shell's Kotlin
sources still imported `dev.shellwright.shell.R`. Keeping the namespace fixed
means the Kotlin sources are copied verbatim and never rewritten.

## Consequences

The generator is small, and most of the Android app is plain compilable Kotlin
that was never touched. A reviewer reads the shell to understand what customers
get. Adding a config field is usually a template edit, not a code change.

The cost is that determinism is now a property somebody has to maintain rather
than one the design gives away. Sorted collections, an invariant culture, LF
endings, explicit permission bits, no timestamp in any hashed file — each is
individually trivial and none is visible in review, so each is asserted by a
test that runs on every pull request.

Three mechanisms defend the arrangement, and they catch different things:

| Mechanism          | Catches                                      | Cannot catch                            |
| ------------------ | -------------------------------------------- | --------------------------------------- |
| Unit tests         | Escaping rules, sorting, cache-key behaviour | Whether the output compiles             |
| Golden snapshots   | Any change to generated bytes, reviewably    | Whether the output compiles             |
| Nightly real build | Whether the output compiles                  | Anything it does not have a fixture for |

⚠️ The third is not optional, and Sprint 04 proved it immediately: the
`namespace` bug above passed all 71 unit tests and every golden file, because a
snapshot records what the generator produced, not whether Gradle accepts it.

The risk that remains is template drift, which the sprint plan rates high and
which is the reason for the one-directory rule. If `shells/android` is ever
forked into a separate template tree, the fork will look correct for about a
sprint and then start failing for customers on code that works perfectly in this
repository. The test that asserts the committed shell equals its own rendering
is what makes that fork fail loudly instead.
